# Публикация Allmaz.Shop на RelaxDev + CI/CD через GitHub

Составлено по документации RelaxDev (деплой, Docker, переменные, базы данных, домены, хранилище, тарифы, превью, персональные данные).

## 0. Прежде чем начинать

**Тариф: TRIAL → PRO.**
- TRIAL: 500 ₽ на баланс при регистрации — это ~15 дней PRO. Деньги начинают тратиться, только когда вы создали свой проект: **сначала подготовьте репозиторий, CI и домен, проекты на платформе создавайте в последнюю очередь**.
- PRO: 990 ₽ за месяц, списывается по 33 ₽ в сутки; 10 проектов (нам нужно 2), PostgreSQL (1 кластер, до 5 баз), Storage API, CDN 5 ГБ, 100 деплоев в день, откат, свои домены с SSL, до 1 000 000 запросов в сутки.
- **Когда баланс заканчивается:** приходит письмо, через 24 часа проекты останавливаются, а через месяц после остановки удаляются вместе с данными. Включите автопополнение или пополните баланс заранее, до конца пробного периода. Тариф меняется в профиле.

**Персональные данные.** В магазине вы обрабатываете данные покупателей (имена, адреса, телефоны). Платформа заявляет, что подходит для их хранения (данные и код — в РФ, ЦОД Timeweb в Москве, через CDN — Yandex Cloud), но на странице тарифов прямо советует для продакшена с данными пользователей использовать «Панель Prod» (ваш сервер под управлением панели, 300 ₽/мес + сам сервер). Если вы оператор персональных данных, нужно уведомление в Роскомнадзор (RelaxDev подаёт его за 5 000 ₽; в документации есть подсказки по заполнению). Это не юридическая консультация — уточните у юриста; технически из общей платформы на «Панель Prod» проект переносится из настроек.

**Нужен свой домен** с доступом к DNS: вход держится на cookie, которую выдаёт API, а читает и API, и сервер Next.js. Это работает только на поддоменах одного родительского домена (`allmaz.shop` и `api.allmaz.shop`). На адресах `*.relaxdev.ru` вход не заработает, а `COOKIE_DOMAIN=.relaxdev.ru` ставить нельзя — cookie ушла бы на чужие проекты.

## 1. Схема

```
PR ──► main ──► GitHub Actions (CI) ──успех──► ветка production ──webhook──► RelaxDev (сборка на их раннерах)
                типы, миграции на чистой БД,                                 ├─ проект allmazshop-api (APP=api)  ── PostgreSQL
                сборка API и Web                                             ├─ проект allmaz-web    (APP=web)
                                                                             └─ Storage (CDN) — картинки и видео товаров
```

На сервер попадает только код, прошедший CI: платформа следит не за `main`, а за веткой `production`, которую двигает GitHub Actions. Redis не нужен (в коде не используется).

## 2. Что уже в репозитории

| Файл | Назначение |
|---|---|
| `Dockerfile`, `.dockerignore` | Один образ на оба сервиса; что запускать — переменная `APP` (`api`/`web`). NODE_ENV=production выставляется в финале (платформа на время установки ставит development) |
| `.github/workflows/ci.yml` | Типы API/Web, миграции на чистой PostgreSQL, сборка API и Web |
| `.github/workflows/promote.yml` | После успешного CI на `main` переносит коммит в `production` |
| `apps/api/src/media/remote-storage.ts` | Загрузка файлов товаров в хранилище RelaxDev, если задан `STORAGE_API_KEY` (иначе — локальный диск, как при разработке) |

Правки под платформу: порт из `PORT`; все переменные API читаются как `process.env['ИМЯ']` (платформа подставляет `auto-generated-stub-for-build` вместо необъявленных переменных, найденных в виде `process.env.ИМЯ`; запись в скобках она не трогает); исправлено: `UPLOADS_DIR` теперь учитывается и при загрузке, а не только при раздаче файлов.
Dockerfile не запускался (в моей среде нет Docker). Образ получается крупным (>1,5 ГБ — платформа лишь подсказывает про это в логе; оптимизацию сделаем позже).

## 3. Шаги

### 3.1. GitHub
1. Запушьте проект в `main`. В git должны быть `packages/database/prisma/migrations/` и `package-lock.json`; `.env` — нет.
2. Дождитесь зелёного **CI** (вкладка Actions): следом `promote.yml` создаст ветку `production`. Нужна сразу — `git push origin main:production`.
3. Если promote падает с «permission denied»: Settings → Actions → General → Workflow permissions → *Read and write*.
4. Защита `main` (Settings → Branches): Require a pull request; Require status checks → **«Типы, сборка, миграции»**; запретить прямой push.

### 3.2. DNS-домен (подготовка, до создания проектов)
Домен `allmaz.shop` должен быть у регистратора с доступом к DNS; NS — родные (регистратора или Cloudflare). Если используете Cloudflare — записи только в режиме «DNS only» (серое облако). Почтовые записи (MX, SPF, DKIM) не трогайте.

### 3.3. Проект `allmazshop-api`
1. «Добавить проект» → подключите GitHub-аккаунт в профиле → репозиторий → ветка **`production`**.
2. **Папку (rootDir) не выбирайте** — оставьте корень: выбор подпапки отрезает остальной репозиторий от сборки, а монорепо нужны `packages/*`.
3. Сборка: **выключите «Автоопределение стека» и выберите «Свой Dockerfile»** (тип «Docker») — иначе ваш Dockerfile игнорируется.
4. Во вкладку «Переменные» вставьте целиком (свои значения; `DATABASE_URL` не добавляйте — его создаст платформа):
```env
APP=api
JWT_SECRET=<openssl rand -hex 48>
JWT_EXPIRES_IN=7d
FRONTEND_URL=https://allmaz.shop
CORS_ORIGINS=https://allmaz.shop,https://www.allmaz.shop
API_PUBLIC_URL=https://api.allmaz.shop
COOKIE_DOMAIN=.allmaz.shop
THROTTLE_LIMIT=1000
UNPAID_ORDER_TTL_MINUTES=120
SHOP_TIMEZONE=Europe/Moscow
SMTP_HOST=
SMTP_PORT=
SMTP_USER=
SMTP_PASS=
SMTP_FROM=
YOOKASSA_SHOP_ID=
YOOKASSA_SECRET_KEY=
```
`PORT` ставит платформа (8080), `NODE_ENV=production` задан в Dockerfile. Определите все ключи (даже пустые) — иначе платформа подставит заглушки.
5. Вкладка **«Базы данных» → «+ Добавить базу» → PostgreSQL**: платформа создаст отдельную базу и пользователя и сама пропишет `DATABASE_URL` во «Переменные». Проверьте переменную и нажмите **«Редеплой»**. Тумблер «Сборка с доступом к БД» не нужен: миграции применяются при старте контейнера (`prisma migrate deploy`).
6. «Деплой». Проверка: `https://<имя>.relaxdev.ru/health` → `{"status":"ok"}`; в логе сборки есть результат проверки порта 8080.

### 3.4. Хранилище для картинок и видео товаров
Файлы контейнера не переживают деплой, поэтому загрузки уходят в Storage RelaxDev (раздаются через `cdn.relaxdev.ru`).
1. В проекте API откройте менеджер файлов → вкладка **«API Доступ» → «Сгенерировать ключ»**. Ключ сам запишется в переменные проекта как `STORAGE_API_KEY`.
2. «Запустить редеплой». С этого момента админка при загрузке файла отправляет его в хранилище, а в БД сохраняется ссылка CDN. Удаление товара/файла удаляет и файл в хранилище.
3. Лимиты PRO: CDN 5 ГБ (ссылка CDN — для файлов до 100 МБ; в админке лимит файла 20 МБ). Изображения платформа сама конвертирует в WebP.
4. Ключ даёт право записи и удаления — храните только в переменных проекта, не в коде и не в браузере.

### 3.5. Проект `allmaz-web`
Тот же репозиторий, ветка `production`, «Свой Dockerfile», rootDir пустой. Переменные:
```env
APP=web
API_URL=https://api.allmaz.shop
SITE_URL=https://allmaz.shop
SITE_NAME=Allmaz.Shop
SEO_NOINDEX=true
```
`API_URL`, `SITE_URL` и `SITE_NAME` читаются **при каждом запросе**, пересборка не нужна: после смены переменной достаточно «Быстрого деплоя» (рестарта). Адрес API сервер кладёт в `<head>` страницы (`window.__ENV`), оттуда его берёт браузер. Так сделано потому, что RelaxDev не передаёт переменные проекта в Docker-сборку, и вшитый при сборке `NEXT_PUBLIC_API_URL` превращался в `localhost:4000` (на сайте — «Failed to fetch»). `NEXT_PUBLIC_API_URL` теперь запасной вариант и необязателен.
`SITE_URL` и `SITE_NAME` попадают в canonical, Open Graph, `sitemap.xml` и `robots.txt`. `SEO_NOINDEX=true` закрывает сайт от поисковиков (тестовый стенд, период до запуска) — **в день запуска смените на `false` или удалите переменную** и отправьте `https://allmaz.shop/sitemap.xml` в Яндекс Вебмастер и Google Search Console.
Проверка: в DevTools → Network запросы идут на `https://api.allmaz.shop`, а не на `localhost:4000`.
До запуска магазина можно закрыть сайт паролем: «Настройки» → «Защита паролем».

### 3.6. Домены и SSL
1. В каждом проекте откройте вкладку «Домены» — там IP проекта.
2. У регистратора создайте A-записи: `@` и `www` → IP проекта **web**; `api` → IP проекта **API** (поддомен подключается как отдельный домен со своей A-записью). Других A и AAAA у этих имён быть не должно.
3. Проверьте DNS на dnschecker.org: во всех регионах только нужный адрес (TTL у регистратора может быть до часа).
4. Добавьте домены во вкладке «Домены»: web — `allmaz.shop` и `www.allmaz.shop` (выберите главное имя; второе будет отдавать редирект 301), API — `api.allmaz.shop`. Панель сама проверит DNS. **Не добавляйте домен с неверными записями**: Let’s Encrypt после пяти неудач в час перестаёт выдавать сертификаты для имени — исправьте DNS и добавьте заново.
5. Сертификат выпускается автоматически (обычно за минуту). Затем убедитесь, что переменные из 3.3 и 3.5 совпадают с итоговыми адресами; если меняли `NEXT_PUBLIC_API_URL` — «Пересобрать» web.

### 3.7. Первый запуск
`db:seed` в production **не запускайте** (создаёт `admin@example.com / admin12345`). Администратор: зарегистрируйтесь на сайте → в панели откройте «Базы данных» → проект → PostgreSQL → **«Студия: таблицы и запросы»** (SQL-редактор в браузере) и выполните:
```sql
UPDATE "User" SET role = 'ADMIN', "isVerified" = true WHERE email = 'ваш@email';
```
Категории, товары и промокоды заведите через админку. (Доступ к БД с компьютера — вкладка «Доступ к БД»: добавьте внешний IP в белый список и закройте порт, когда закончите.)

### 3.8. Бэкапы базы
PostgreSQL бэкапится каждую ночь, копии хранятся 3 дня. Перед миграцией создавайте копию вручную (вкладка «Бэкапы» → «Создать бэкап»). Рекомендую настроить копию в своё закрытое хранилище (S3 или WebDAV, например Яндекс Диск с паролем приложения) — раз в 3–24 часа.

### 3.9. Почта и ЮKassa
- Тестовое письмо — регистрация нового пользователя; при `ETIMEDOUT` в логах смените порт/провайдера SMTP.
- ЮKassa → Интеграция → HTTP-уведомления: `https://api.allmaz.shop/payments/yookassa/webhook`, события `payment.succeeded`, `payment.canceled`. Боевые ключи — в `YOOKASSA_*` (если пусты, код использует тестовые). Если включена защита паролем на API, откройте путь вебхука в исключениях; на сайт (web) защита вебхуков не влияет.

## 4. Как работает CI/CD

| Событие | Что происходит |
|---|---|
| Pull Request | CI: зависимости → Prisma Client → пакеты → типы API и Web → **миграции на пустой PostgreSQL** → сборка |
| Merge в `main` | CI ещё раз; при успехе `promote.yml` двигает `production` |
| Обновление `production` | Вебхук → RelaxDev собирает оба проекта (сборки проекта идут по очереди, до 5 одновременно) и выкатывает |
| CI красный | `production` не меняется |

- **Деплой без простоя** включён для веб-проектов: новая версия запускается рядом, трафик переходит после готовности порта 8080. Несколько секунд работают обе версии, поэтому меняйте схему БД совместимо: сначала добавить колонку, удалять старую — следующим релизом.
- **Откат:** история деплоев → «Откатить» (тот же образ без сборки, секунды); конкретный коммит — стрелка рядом с «Редеплой». **Миграции БД не откатываются** — перед рискованными сделайте бэкап.
- **Превью веток** (вкладка «Окружения» → ветка → «Создать»; адрес `проект-git-ветка.preview.relaxdev.ru`, живёт 72 часа, до 5): по умолчанию использует **боевую базу** — переключите «Переменные и БД» на **«Только схема»** (миграции накатятся при старте). Переменные превью наследуются от продакшна — нажмите «Скопировать из продакшна» и подставьте тестовые ключи ЮKassa. Из-за вшитого адреса API превью сайта обращается к боевому API: используйте превью осторожно.
- **Секреты** хранятся только в панели RelaxDev; секреты GitHub не нужны. Диагностика: лог сборки в истории деплоев (при ошибке панель даёт подсказку), логи приложения за 7 дней; в панели есть чат поддержки (помощь с деплоем входит в PRO).

## 5. Типичные проблемы

| Симптом | Причина / решение |
|---|---|
| Сборка идёт «не по нашему Dockerfile» | Тип сборки не «Docker» / включено автоопределение |
| `COPY failed: file not found` | Выбрана подпапка (rootDir) — уберите |
| 502 Bad Gateway | Приложение слушает не `PORT`/`0.0.0.0`; результат проверки порта — в логе сборки |
| В значениях `auto-generated-stub-for-build` | Переменная не добавлена во вкладку «Переменные» (баннер «Переменные без значения») |
| Сайт ходит на `localhost:4000` | `NEXT_PUBLIC_API_URL` не попал в сборку (п. 3.5) |
| Вход «проходит», сайт видит гостя | Нет `COOKIE_DOMAIN` или сайт и API не на общем родительском домене |
| Ошибка CORS | `CORS_ORIGINS`/`FRONTEND_URL` не совпадают с адресом сайта (`https://`, без `/` на конце) |
| `P3005 schema is not empty` | В БД чужие таблицы — используйте чистую |
| Загрузка файла → 502/«Хранилище недоступно» | Нет/неверный `STORAGE_API_KEY` или не сделан редеплой после генерации ключа |
| 429 Too Many Requests | Поднять `THROTTLE_LIMIT` |
| Promote падает при push | Ветка `production` разошлась с `main` или у Actions нет прав записи |
| После окончания пробного периода проекты остановились | Не пополнен баланс; пополните — запустятся сами (в течение месяца) |

## 6. Порядок работ (чек-лист)
1. Репозиторий на GitHub, зелёный CI, ветка `production`, защита `main`.
2. Домен и доступ к DNS, SMTP-провайдер, боевые ключи ЮKassa (позже, на тестовых можно проверить заказы).
3. Создать проект API → база → переменные → хранилище → деплой.
4. Создать проект web → переменные → деплой.
5. Домены и DNS → сертификаты → пересборка web при смене адреса API.
6. Администратор, тестовый заказ, письма, вебхук ЮKassa, проверка картинок после редеплоя.
7. Пополнить баланс / включить автопополнение до окончания пробного периода.
